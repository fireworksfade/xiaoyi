# ESP32 Watchdog 与任务阻塞诊断

来源：Espressif ESP-IDF Watchdogs 与 Fatal Errors 官方文档。
适用范围：ESP32、FreeRTOS、ESP-IDF 5.x/6.x。

## Watchdog 类型

Interrupt Watchdog 用于发现中断或临界区长期阻塞，典型日志包含 Interrupt wdt timeout、CPU 编号和寄存器转储。Task Watchdog 用于发现任务长时间不让出 CPU，常见日志会列出未及时复位看门狗的任务。RTC Watchdog 还可能在启动或 Panic 处理阶段超时。诊断时必须保留完整错误名称，不能统一写成“看门狗重启”。

## 常见根因

中断服务程序执行耗时操作；在禁中断或临界区中进行网络、Flash 或大循环处理；高优先级任务没有 delay、阻塞等待或主动 yield；任务死循环；锁等待形成死锁；Flash 擦写期间执行了不满足 IRAM 要求的代码；单次计算、压缩或解析耗时超过 watchdog 配置。

Task Watchdog 报错不一定表示触发日志的任务就是根因。某个高优先级任务占满 CPU 后，空闲任务无法运行，也会被报告。应结合两个核心的任务列表、Backtrace、任务优先级和运行时间分析。

## 确认步骤

第一步记录 watchdog 类型、CPU、任务名、触发时间和完整 Backtrace。第二步用对应固件 ELF 解码调用栈。第三步检查栈顶代码是否位于 ISR、临界区、Flash 操作、网络回调或没有阻塞点的循环。第四步测量关键代码实际执行时间，不要只根据代码长度估计。第五步记录同一时间的 heap、WiFi、MQTT 心跳和队列长度，判断连接超时是否是任务阻塞的次生故障。

## 修复方法

ISR 只完成必要操作，把耗时处理投递给普通任务。缩短临界区，拆分长循环并周期性让出 CPU。避免在持锁状态执行网络请求或阻塞 I/O。Flash 操作相关路径遵守 IRAM 与缓存限制。只有确认任务正常但合法执行时间确实更长时，才调整 watchdog 超时；单纯增大超时会掩盖死循环和优先级错误。

## 验证方法

使用原始负载和峰值负载连续运行，监控任务运行时间、空闲任务执行情况、MQTT 心跳和 watchdog 计数。验证断网重连、传感器超时和 Flash 写入等错误路径，因为阻塞问题往往只出现在异常处理或重试循环中。
